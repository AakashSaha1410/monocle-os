# Architecture and hosting

**What this is.** How the platform is proposed to run, and why each piece is there.
Written against the process in `01-the-process.md` and the schema in
`09-database.md` — every choice below exists because something in the process
needs it.

**What this is not.** A cost estimate or a commercial proposal. Sizing and budget
are handled separately.

---

## The shape

A container running the API, a managed PostgreSQL database, and object storage for
the files. Everything else is there to keep those three safe, observed and
recoverable.

| Layer | Service | Why the process needs it |
|---|---|---|
| DNS | Route 53 | The platform and the borrower portal need stable addresses |
| Edge protection | AWS WAF | The borrower portal is reachable by anyone with a link; it needs rate limiting and managed rules in front of it |
| Load balancing | Application Load Balancer | HTTPS termination and health-checked routing to the API |
| Application | ECS Fargate | Runs the API as a container. No servers to patch. Scales from one task to several without an application rewrite |
| Database | Amazon RDS for PostgreSQL | The loan record, the needs list, every status change and every email. See `09-database.md` |
| Documents | Amazon S3 | The files themselves. The database holds keys, versions and checksums — never file bytes |
| Encryption | AWS KMS | Keys for the database and for document storage |
| Secrets | AWS Secrets Manager | Database credentials, DocuSign and Lightning Docs credentials — never in source or environment files |
| Background work | Amazon SQS with a dead-letter queue | Every email send, DocuSign envelope and Lightning Docs generation is queued, retried and never duplicated |
| Monitoring | Amazon CloudWatch | Logs, metrics and alarms on errors, unhealthy tasks and database health |
| Infrastructure audit | AWS CloudTrail | Who changed the infrastructure. Separate from the platform's own audit trail |
| Backup | AWS Backup and RDS automated backups | Recovery and retention, set to whatever the lender's retention obligations require |

## Why these, for this process

**PostgreSQL rather than anything lighter.** The needs list is generated by rules
over permutations; the pipeline is a live query across every loan; the reporting
views compute days-in-status and the calculated funding date. That is relational
work with real constraints, and the constraints are what stop the process being
skipped — the Processing gate and the No Fly block are enforced in the database and
the API, not in the interface.

**S3 rather than storing files in the database.** A socket can hold several files
and nothing is ever deleted — three months of bank statements are three files, a
replaced document keeps its predecessor. S3 versioning does that natively, and
keeps the database small enough to stay fast.

**A queue in front of every outside call.** DocuSign, Lightning Docs and the mail
provider all fail occasionally. Every one of those calls is a row in
`integration_outbox` with an idempotency key before it is attempted, so a retry
can never send the LOI twice or generate a second set of loan documents.

**A read replica for reporting.** The `reporting` schema — Pulse, outstanding
items, cycle times, vendor drift — is served from a replica through a role that can
only SELECT. The pipeline is the report the business is run from, and it can never
slow down or corrupt the transactional side.

## Security and data protection

- The database sits in private subnets and is not publicly reachable.
- Document storage has public access blocked and server-side encryption with a
  managed key. Versioning is on, so replacing a document never destroys the
  original.
- Credentials live in Secrets Manager, not in source control or environment files.
- The public entry point sits behind the firewall with managed rules and rate
  limiting.
- IAM follows least privilege — the application task holds only the permissions it
  actually uses.
- Infrastructure changes are audited by CloudTrail; **business** actions are
  audited by the platform itself, in the append-only `events` table. Those are two
  different questions and both are answered.
- Personal data — dates of birth, identity numbers, guarantor notice addresses — is
  marked in the schema, encrypted at rest and masked on screen.
- Backup and retention are configured to the lender's own legal and regulatory
  requirements. The schema carries `legal_hold` and `retention_until` on documents
  so a hold can be honoured before any retention policy runs.

---

## Reliability

- Standard API error responses carry an HTTP status, a validation message and a
  correlation id. That same correlation id is written to the audit trail, so one
  request can be traced end to end.
- Operations that must not happen twice — document generation, status transitions,
  sending the LOI — are idempotent.
- Integration failures retry on a controlled policy; what permanently fails lands
  in the dead-letter queue for someone to look at rather than disappearing.
- Alarms watch application errors, unhealthy tasks and database health.

## Growing into it

The same architecture runs at two sizes. Nothing about the application changes
between them.

| | Starting configuration | High availability |
|---|---|---|
| Application | One container task | Two or more, across availability zones |
| Database | Single availability zone | Multi-AZ |
| Outbound networking | One NAT gateway | Multi-AZ, as required |
| Load balancer | One, single zone | One, distributed across zones |
| Backups | Automated, with a retention policy | Automated, with extended retention and disaster recovery |

Move when monitoring says to, not in advance. The application is written to scale
horizontally from the first day, so the upgrade is configuration rather than work.

**One networking note worth knowing early:** a NAT gateway is a fixed cost that
does not shrink with low traffic. VPC endpoints carry traffic to AWS services
without it and are worth configuring where they apply.

## What is deliberately not here

- **No AMC interface.** Where an appraisal management company has its own ordering
  system, staff update the status by hand. No vendor's process is settled enough to
  build against.
- **No mailbox reading.** The platform sends and logs; replies arrive in Outlook
  and a person records the outcome. Reading the mailbox is a later phase and needs
  a different set of permissions entirely.
- **No embedded credit or background retrieval.** Those pulls happen outside; the
  platform records the result.
- **No model hosting.** The intelligence layer is a later phase, and private model
  hosting is a condition of doing any of it with borrower financial data. The
  schema reserves the tables so nothing has to be rebuilt.
